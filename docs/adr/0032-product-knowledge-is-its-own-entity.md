# 产品知识自己一张表,不是知识集那几张表的扩展

产品知识(CONTEXT.md 产品知识,spec #342)是第二层知识:一条陈述说的是产品内两个以上仓库之间的事,范围键是涉及的仓库集合。知识集那一层的范围键是「一个仓库 + 一个 glob」,`review_rule`、`rule_set_version`、`rule_proposal`、`rule_proposal_source`、`rule_trace` 五张表与整条评审链路都按这个键写成。选定的做法:**产品知识是自己的实体,`product_knowledge` 一张表挂在产品上,知识集那几张表与评审链路一行不动。** 仓库集合存成这一行里一段升序去重的 repo id JSON,不另开关联表。

## Considered Options

- **把 `review_rule.repo_id` 改成可空,产品知识作为「没有仓库的条目」住进去。** 省一张表,但这个键一放空就传染五张表与每一条评审查询:取一个仓库生效知识集的那几句 `WHERE repo_id = ?` 要各自决定「空的那些算不算」,知识集版本的快照语义(一次裁决之后共同生效的那一份)也要跟着解释产品级条目属于哪个版本——而产品知识根本不注入评审,它只进 Agent 会话。一个读不到它的链路为它改五张表,代价与收益不成比例。
- **仓库集合另开一张 `product_knowledge_repo` 关联表。** 关系范式上更正,也能用 SQL 做交集查询。但一条条目的仓库集合写下来就不再变:产品摘掉一个仓库时那条条目整条退役,不是改它的集合(spec #342 的仓库集合有效性)。不变的集合不需要一张有自己生命周期的表,而 `query_knowledge` 的交集是在一个产品那几十条条目上做的,应用层一次 filter 就够,省掉一张表与它的级联删除。

## Consequences

- `product_knowledge` 的状态三态(提案 / 生效 / 退役)与 `retires_id`、`proposed_session_id` 几格在 issue #343 里只有生效与退役两条路走得通:手写即直接生效,退役是一次状态变更。提案确认、驳回记忆与产品梳理会话(issue #344–#347)填上其余几格,表结构不必再改。
- 产品知识不进 Review Run:评审的知识注入与冻结事实一行未动,知识集版本不包含产品知识。
- 仓库集合的校验落在写入口:去重之后至少两个、且都在这个产品当前的仓库里。库里只保证它是一段 JSON 数组。
- 产品是它唯一的挂载点,删产品连同它的条目一并硬删(与产品下的 Agent 会话同律)。
- 交集查询在应用层做,条目数随一个产品的迭代次数增长;真大到扫不动时再换关联表,那一步只动读法,不动已有的行。
