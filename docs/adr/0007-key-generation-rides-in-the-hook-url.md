# key 代次写进 hook URL,轮转状态从 Gitea 推断

Gitea 改不了已有 hook 的 secret(`PATCH` 静默忽略 `config.secret` 并回 200,见 `docs/research/gitea-webhook-api.md:126-151`),也从不回显它——`ToHook` 只往 `config` 里塞 `url` 与 `content_type`(同上,第 241-264 行)。于是 key 轮转必须删旧建新,而「库里的 key 与 Gitea 上的 secret 是否一致」在正常途径下不可观测。

`config.url` 是唯一双向可见的字段:面板写得进,列表读得回。因此每个仓库的 key 带一个**代次**——一个单调递增的整数,写进 hook URL 的 `?k=` 参数。一次 `GET .../hooks` 就读出 Gitea 上装的是第几代,不必等一次投递验签失败才发现不一致。

代次可读之后,轮转不再需要状态机:库里的 key 列表与 Gitea 上的 hook 代次一比,唯一确定下一步该做什么。轮转因此是**可重入的单调推进**,不是必须原子完成的事务。

## Considered Options

- **库里存一条 rotation 记录(`pending` / `created` / `deleted`),重试读它。**多一份状态,而它会和现实脱节——人在 Gitea UI 里手删了 hook,库里仍写着 `deleted`。真相在 Gitea 上,再存一份等于给自己造一类新的不一致。
- **URL 不带代次,不一致靠投递验签失败暴露。**沉默期长得不可接受:一个当周没有 pull request 的仓库,坏掉的 hook 要到下次有人提 PR 才现形,且现形的方式是审查没跑。

## Consequences

- **先建后删,不留无 hook 窗口。**两条 hook 并存期间同一个 head commit 投递两次,被现有幂等吃掉——`claimDelivery` 的键是 `(owner, repo, head_sha)`(`src/review/store.ts:331-334`),不是 Gitea 的投递 id。先删后建才要付出投递丢失的代价,这里没有理由付。
- **验签按 URL 上的代次取 key。**代次来自请求方因而不可信,但它只当索引,验签仍然决定一切:取错就是 401。这让服务能把「未注册仓库」与「用已废弃的第 n 代签的」分成两类 401 记录。
- **每个仓库最多两把 key。**点轮转时若上一轮没收尾,先把上一轮推到底,再开新一轮,代次不堆积。
- **新代次取 `max(库里最大, Gitea 列表里读到的最大) + 1`。**库被回滚到旧备份时,Gitea 上的代次会高于库里;从 Gitea 侧取上界让这种状态点一次轮转就自愈,不必人工介入。
- **删 hook 回 404 算成功。**删除不幂等(`docs/research/gitea-webhook-api.md` 第 5 节),但 404 的语义就是目标已达成。
- **删除仓库时 hook 删不掉就不让删。**注册表里没有记录必须蕴含 Gitea 上没有本服务的 hook;放行会留下一条永远拿 401 的孤儿 hook,而它已经不在面板的任何视图里。守住这条,「有 hook 无记录」这个中间态根本不存在。
- **核对在打开仓库配置弹窗时做,发现不一致只展示、不自动修。**读页面不产生副作用。代价是坏掉的仓库要等人看一眼才会被推回一致,而这是可接受的:面板本来就是人工界面,且不做自动轮转——轮转周期是运维策略,不是本服务的功能。
