# 评审规则存产品数据库,人始终在修订闭环

> 2026-09-08: 合并放宽到单目标(issue #289,父 spec #286):合并指向一条以上现有条目,型由新陈述定。上一条写的「多条目标」因此改口——一条目标而新陈述的型与它不同就是改型,走合并。修改那一档不许翻型的闸保留,改型于是有了一条一次裁决完的路径,不必「废止 + 新增」两条提案排两回队;采纳与多目标同一条路径:目标废止于新版、新条目以新的型生效于同一版。
> 2026-09-08: 变更类型多一档「合并」(issue #282,父 spec #280):多条目标条目换一条新陈述。原来三档(新增 / 修改 / 废止)下,几条说同一件事的条目只能靠人一条条废止再新增一条,一次合并要裁决三四回,而中途每一次采纳都会让剩下几条的目标失效。合并因此成为一条提案:采纳即目标全部废止于新版、合成的那一条生效于同一版,任一目标已不生效就采纳不了(与修改型同一句话),驳回照常。**提案的目标随之从一个变成一列**,`propose_rule` 的目标参数改为可给多个,三条链路共用同一套映射。存库、人在闭环、提案裁决等其余决策继续有效。
> 2026-09-08: 「agent 在任何路径上都不直接修改知识集」之外多一条:**agent 直接改待裁决队列**(issue #284,父 spec #280)。知识整理是人手动发起的第三条规则 agent 链路,读现集与待裁决队列,把重复的提案合成一条、把现集已经有的新增改写成指向那条的修改。这不破防腐律——被它动的是队列,不是知识集:每一条提案仍要人裁决才落进知识集,整理只让人少读几遍同一件事。落地逐条校验(被并的提案不再待裁决即跳过、目标条目不生效即丢弃),整理期间裁决与处置照常,因此不冻结任何人的工作。
> 2026-09-08: 知识整理还对现集提出变更(issue #285,父 spec #280)。它一次读完全部生效条目,看得见知识集自己积下的重复与矛盾;这些变更走的仍是修订提案队列——合并、修改或废止,出处记知识整理,人裁决才落进知识集。防腐律因此原样成立:直改只对还没人裁决的队列成立,知识集这一侧照旧只由裁决改动。

> 2026-09-08: 「每条提案标注出处」改为「每条提案带一列出处附注」(issue #281,父 spec #280)。一条提案会被多次来源提到——反哺并入、知识整理合并——单值出处只留得下一次,而人要看的正是它被哪几件事提过。出处因此下沉为附注列表:一行一条,自带来源(基点探索 / 处置反哺 / 知识整理)、备注原文、Finding 引用与知识轨迹。**重探索的覆盖范围随之收窄**为「待裁决且附注全部来自基点探索」:人写下的处置备注不该被一次重探索抹掉。存库、人在闭环、提案裁决等其余决策继续有效。

> 2026-08-31: 「规范与描述分离」(描述性条目不入集)与「产出至多 30 条」两款由 ADR 0020 取代——知识集以 type 隔离容纳评审规则与项目事实,探索产出改为批量确认。存库、人在闭环、提案裁决等其余决策继续有效。

Reviewer 的 prompt 原来是写死的,没有任何渠道告诉它「这个仓库审什么、怎么审」——架构分层、安全清单、团队约定这类仓库级评审指引在产品里没有位置。补这个缺口有一条显而易见的轻路线:约定被审仓库放一份 REVIEW.md,Reviewer 反正持有完整工作副本,读它即可,零 schema、零面板。我们没有走它,而是把评审规则做成产品数据库里的一等实体:规则集按仓库存库、整组版本化,Review Run 开始时冻结一个规则集版本(与模型服务版本同律);规则由基点探索推导、由人整组确认后生效;此后一切变更——重探索的产出与处置反哺的解读——都以修订提案的形态排队,人裁决采纳才落,agent 在任何路径上都不直接修改规则集。

选存库是因为规则的核心操作是治理而非阅读:逐条确认、增删改、提案裁决、出处追溯、版本冻结,这些仓库文件一样都给不了;规则表达的是团队现行标准,评审历史 tag 也该按现行标准执行,「规则与代码同版本化」恰好是这里不想要的性质。选人在闭环是防腐:处置信号天然含混(一次 resolve 分不清修了、接受风险还是不认同规则),让 agent 凭它静默改规则集,规则集必然在长期使用中长成自相矛盾的例外堆。同一防腐律的另一半是规范与描述分离:规则集只收「应当怎样」的规范性陈述,基点探索得出的架构地图是确认时的参考产物,描述性事实会随代码演进变成谎言,不入集。

## Considered Options

- **仓库内 REVIEW.md 约定。**最小实现,规则随代码版本化,作者自己维护。但确认流、提案裁决、版本冻结、命中统计全都无处安放,处置反哺更是无从谈起;规则治理权也从面板的权限体系旁落到任何能向仓库提交的人。
- **agent 直接更新规则集,人事后抽查。**反哺链路最短,但把含混的处置信号直接写成规则,错一次就以规则的身份影响之后每一轮评审;抽查发现时已经污染了统计与裁决历史。
- **描述性架构地图与规范性规则同存一集。**探索产出照单全收最省事,但地图类条目(「service 层在某目录」)随代码演进过时,规则集的可信度被最先腐烂的那部分拖垮。

## Consequences

- CONTEXT.md 新增九个术语:评审规则、规则集、规则集版本、基点探索、规则草案、修订提案、处置反哺、裁决、规则确认。
- 权限格新增 `rule:write`(第 9 格),管规则确认、增删改与提案裁决;读侧沿用「登录 + 仓库分配可读」,不设 `rule:read`。
- 新注册仓库完成规则确认前不执行 Review Run;升级前已注册的仓库视同已确认空规则集,行为零变化。
- 处置反哺只由带处置备注的处置触发:无备注的 resolve 语义含混,不构成反哺输入。这收窄了反哺覆盖面,是有意的取舍。
- 基点探索产出按重要性截断为至多 30 条:上限的本质是人一次确认得完、不麻木;宁缺勿滥,缺的靠反哺补。
