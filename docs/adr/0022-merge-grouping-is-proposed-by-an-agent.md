# 合并分组由 agent 提议,检出率由代码守恒

「这两条 Finding 说的是不是同一回事」是语义判断。评审流水线里其余的语义判断(审查、取证、复核、知识探索)都已由 agent 承担,只有合并去重仍在用词面重叠冒充语义:token Jaccard 加 0.05 的阈值对语义无感,「删除余额校验」与「删除类型校验」共享四个字就被判成同一个问题(PR #21 实测),而同一个缺陷的两种纯中文改写可以一个 token 都不共享。阈值调不动这件事:两类样本的取值本来就重叠(ADR 0015 与 `dedupe.ts` 的注释记着这条实测)。

因此新增一个合并 agent:每轮 Review Run 汇齐全部成功 Reviewer 的 Finding 之后跑一次,它读内容、必要时翻代码,给出分组方案——哪些条目是同一个问题,每组附一句理由。编排层只认一个 `MergeAgent` 接口(与 `Reviewer`、`RuleAgent` 同构),真实实现是 Pi 子进程,测试注入脚本化实现。

**委托出去的只有语义那一半。**代表段、行号(组内最小)、严重度(最高)、分类(首报)、归属保留与逐字重复折叠仍由 `dedupe.ts` 派生,与 ADR 0015 修订后逐字一致;呈现语义不变,变的只有「怎么分组」。

**检出率由代码性质保证。**分组方案要过三条硬性质,任一违反即整份作废:每条输入 Finding 恰好出现在一组(不丢不重)、组内成员同文件、组内每个成员与至少一个其他成员行距不超过现行容差。位置语义(「同一处」)因此不交给模型,合并只改语义判据这一半。

**回退是整体的。**agent 失败、超时或验收不过,整轮的合并退回现行算法,并在审查轨迹记一条回退事件。最坏情况恒等于这一票之前的行为。

## Considered Options

- **继续调阈值或换相似度算法。**字符 bigram、词向量都仍是词面,`dedupe.ts` 的实测记录表明两类样本在这类信号上重叠;换算法只是换一个重叠位置。
- **让 Reviewer 自报同一缺陷的稳定标识。**几个模型无法协调命名,标识只在同一个模型内部稳定;跨模型合并正是它管不到的那一半。
- **部分采纳分组方案(验收不过的那几组退回算法,其余保留)。**混合结果的检出率不再有可陈述的性质:哪几条被谁分的组要逐条追,而检出率是本仓库要守住的那个量。
- **合并 agent 单配一处模型。**多一个配置面与一份凭据面,而这一次判断与本轮审查同质;取配置序第一个 Reviewer 的模型快照与凭据即可,零新增配置。

## Consequences

- 本 ADR 取代 ADR 0015 修订后的**纯算法合并判据**;0015 的其余部分(Finding Identity 去掉 Reviewer、归属全保留、严重度取最高、分类取首报、统计以审查阶段为主维度)继续有效。词面判据(`sameSpot` 的同一行与行距加相似度两档)不删除,它是回退档,阈值维持 0.05。
- 同一份输入两次跑可能给出不完全一致的分组,评论条数在重跑之间可能跳。已知代价,以准确性换取。
- 合并 agent 的 token 用量计入本轮总量(`review_run` 的用量列),不落 `reviewer_outcome`——它不是 Reviewer,记成一行会让按模型的统计多出一个不存在的模型。逐 Reviewer 那几行与本轮总量的差额就是它。
- 审查轨迹多两档轮次级事件(`merge_agent_finished`、`merge_fallback`),合并事件的判据多一档 `agent`(带理由原文);合并 agent 的会话事件以固定名字进 Reviewer 级轨迹,与 Reviewer、取证同一待遇。
- 一轮 Review Run 多一次模型调用与一个子进程,时间与花费相应增加;不足两条 Finding 时不派。
- 跨轮匹配、延续与自动处置的判据不变:内容指纹与 `sameContent` 是机械判定,留在代码侧。

## 2026-09-04 修订:输入扩到同文件历史,折叠与延续两条一并收口(issue #237)

上面最后一条不再成立。合并 agent 只看本轮,因此跨轮次的重报仍只有那两道机械判定挡着:指纹折叠要求落点前后 3 行的内容 hash 相等,增量在那扇窗口里插几行就折不上;延续配对用标题 token 相似度,同一件事换个说法就配不上。线上 `DEV/AI-API` 范围审查 #11 重跑之后,286 条未处置 Finding 里查出 46 个语义重复簇、117 条,同文件那一部分正是这两道漏下来的。语义判断已经有承担者,让它看不见历史是白白浪费。

**输入扩到同文件历史。**合并请求在本轮全部成功 Reviewer 的 Finding 之外,带上本审查阶段的历史 Finding,只取所在文件在本轮有 Finding 报出的那些;未处置与已处置都给,来源与注入 Reviewer 的那一份相同(`store.stageHistory`),不带操作人。体积控制就是这一道路由,不设条数上限。历史在分组方案里用自己的落库 id 作标识,与本轮 Finding 的下标分在两格,agent 仍只回答「哪些条目是同一回事」。

**验收性质分两档。**不含历史成员的组照上面三条硬性质验,本轮新报之间的检出率因此不因带上历史而松动。含历史成员的组只验一条:全部成员同文件,历史成员的旧行号不参与行距计算。行距在这一档免验,是因为代码改写之后同一个问题会漂到离旧位置很远的地方,拿行距去挡等于把这次扩展要接住的那一类全挡掉。历史另有两条:必须是这次给出的历史里的一条,且不得出现在两组里;历史可以不出现在任何一组里——它是候选,不是必须被认领的输入。

**收口仍由代码定,分折叠与延续两条。**一组命中一条历史时:那条历史已经处置过,或它的旧指纹在本轮 head 上仍算得出,即折叠——组内本轮成员挂到它的旧评论上,不新发评论,已处置的那一档因此沉默;旧指纹算不出即延续——组内本轮成员承接它的 Finding Identity,旧评论 resolve 并记「已延续」,新评论正文带「延续自」。一组命中多条历史时取 id 最小的一条作数,其余不动。指纹折叠优先于 agent 命中,agent 命中优先于词法配对与复核结论自带位置的合成:硬证据在前,语义判断补它够不着的那一段,机械配对垫底。

**回退仍是整体的。**agent 失败、超时或方案不过验收,分组退回算法合并,跨轮次折叠退回指纹 ±3 行,延续退回词法配对,轨迹记一条回退事件。最坏情况恒等于这次扩展之前的行为。折叠与延续各发一条轨迹事件,判据分档记明:指纹、词法、复核结论给的位置,或 agent 加它的理由原文。

跨文件同根因的关联是另一个概念,不在这次扩展里。
