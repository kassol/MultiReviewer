# 知识集:评审规则与项目事实同表两型

对另一项目十轮 AI 评审记录(740 条人工决议)的复盘给出两个硬数据:被撤销/降级的误报几乎全部源于 Reviewer 缺少项目事实(全局拦截器的存在、改动是否已发版、实际落库的 SQL 列集),而这些事实没有任何注入渠道;被修复条目的绝对大头集中在少数几类可规则化的缺陷模式。据此把长期评审知识按时态拆为三种:应然(评审规则,违反即 Finding)、实然(项目事实,判断依据,本身不产 Finding,与代码矛盾时以代码为准)、已然(处置先例)。前两者作为知识条目的两型存进同一张知识表,以 type 区分,注入时按型分段渲染;已然不入表——它以 Finding 的处置历史原样存在,处置反哺负责把其中可沉淀的部分蒸馏成规则或事实提案。这推翻了 ADR 0019 的「规范与描述分离」条款:当初拒收描述性条目是因为它会随代码演进腐烂,现在防腐手段从拒收升级为治理——事实型有专属注入语义、可被反哺提废止,误报处置持续冲刷过期事实。

同一决定移除基点探索「至多 30 条」的产出上限(ADR 0019 另一条款):上限的前提是逐条人工确认,确认页改为批量采纳/驳回后前提不再成立。探索的 prompt 相应从「禁报描述性条目」改为按两型分别产出。ADR 0019 的其余部分——知识存产品库、人始终在修订闭环、agent 只产提案不直改——原样继续有效。

## Considered Options

- **维持 ADR 0019 的拒收,事实另想办法。**误报数据表明缺事实注入是最大质量漏洞,拒收等于放着第一根因不治。
- **规则与事实分两张表、两套流程。**两者形状同构(scope + 陈述 + 出处 + 两态生命周期),分表让 CRUD、面板、草案/提案/裁决/版本管线各复制一份,差异其实只在注入模板与消费语义,是一个 type 字段的事。
- **非结构化的 agent 级项目记忆。**没有选择性注入(按 scope 裁剪)、没有失效治理(过期事实导致自信的误判)、且多模型面板共享同一份知识,per-agent 记忆会在模型间碎裂。

## Consequences

- CONTEXT.md 术语上位化:新增知识条目、项目事实、知识集(取代规则集)、知识集版本、知识草案、知识确认、知识轨迹;评审规则降为知识条目的规范型;基点探索、修订提案、处置反哺的定义随之改写。
- 权限格 `rule:write` 改名 `knowledge:write`,存量角色数据一次性迁移。
- Finding 的 ruleId 只允许指向规则型条目,服务端校验。
- 事实来源三渠道同期开通:面板手填、处置反哺蒸馏、基点探索产出;question 类 Finding(评审提问生成事实)延后。
- 注入与规则同律:全量注入、scope 标在条目上由模型自判、录入时限制单条长度,服务端不过滤不截断;体积靠治理(宁缺勿滥、反哺废止),失控再考虑 scope 过滤。
- `RULE_LIMIT` 移除与批量确认 UX 是同一变更的两半,不拆开交付。
