# 批次是 Review Run 的恢复粒度,中间态与统计分开存

一轮 Review Run 被服务重启打断时,各批的结果只在内存里等全部批次跑完才随收尾事务一并写库。进程落地(发版、容器重建)就把已经跑完的批次成果全部丢掉,已经花掉的 token 保不住,重跑只能从头开始。issue #247 把这些轮次改判失败,止住了「永远显示进行中」;本决策定的是它前面那一步——先尝试续跑。

选定的做法:**批次是恢复粒度**。每一批跑完立即把该批各 Reviewer 的结果写进一张只服务「还没收尾的那一轮」的中间态表 `review_run_batch`(键是 `run_id + batch_index`,存这一批的文件清单与各 Reviewer 的结果 JSON);开跑时把本轮用到的历史 Finding 快照写进 `review_run.history_json`。服务启动时对没有结束时间的轮次重新准备工作副本、按同一 head 重新切批,只跑库里缺结果的批次,再走现有的合并、收尾与发评论。收尾仍只做一次,一轮只发一次 review 不变;`finishRun` 在同一个事务里把该轮的中间态行删掉。

恢复粒度取批次而不是更细:Reviewer 的 Pi 会话用 `SessionManager.inMemory()`(ADR 0017),批次跑到一半的会话随进程消失,续不了。(**这一句在 2026-09-21 细化,见文末修订**:续不了的是会话,恢复单位因此是一次完整的 Reviewer 会话,而不是整批。)

## Considered Options

- **每批的结果直接写进 `reviewer_outcome` 与 `finding`。**这两张表是事后统计的来源:处置率、模型参与度、用量都从它们算。中间态混进去,一轮跑到一半的结果就进了分母,而合并、跨轮匹配与自动处置都还没做——那些行既不是最终的 Finding Identity,也没有 resolve 载体。要把它们排除就得给每一行加「这一轮结束没有」的判据,每一处统计各自记得带上它。
- **快照历史不落库,续跑时重读当前历史。**重启期间有人处置了一条历史,续跑的批次拿到的历史就与原轮各批不同:同一轮里前几批被要求复核的条目,后几批看不见了。一轮的注入必须是同一份。
- **把整轮的中间态写成一个 JSON 大对象,每批覆盖一次。**批次受限并行(issue #232)下几批同时结束,读改写会互相覆盖。按批次一行则各写各的,并发天然安全。
- **续跑不核对冻结前提,直接接着跑。**head 变了、分批上限改了、知识集版本推进了、模型组合换了,已落库的批次与新切出的批次就指向不同的文件集或不同的规则,合出来的覆盖是错的。

## Consequences

- 库里多一张中间态表。它只在「开跑到收尾之间」有行:收尾与改判失败都会把该轮的行删掉,长期占用因此不随轮次数增长。
- `review_run` 多一列历史快照。它随轮次永久保留——回看一轮时「当时注入的是哪些历史」从此答得出来。
- 续跑的前提在 `runReview` 里当场核对(head、知识集版本、重新切批的每一批文件清单、Reviewer 组合),任一条不成立即抛,由启动侧退回 issue #247 的改判并写上原因。**续跑不成立是常态之一,不是异常**:管理员在重启期间改了分批上限或知识集,那一轮就该从头重跑。
- 升级前落库的轮次没有历史快照,读回即「不可续跑」,一律退回改判。
- 续跑那一轮的耗时只算续跑这一段:崩溃前跑了多久、进程停机多久都没人知道,拿结束时间减开跑时间会把停机时长也算成审查耗时。(**这一条在 2026-09-21 改口,见文末修订**:崩溃前跑了多久从此有记录,单模型与轮次级都算它,停机仍不算。)
- 启动时逐轮串行续跑:同时续跑几轮会一次开满「批数 × 模型数」个子进程,与批次受限并行防的是同一件事。没有中断轮次时启动路径零改动。

## 修订(2026-09-05)

核对项里的「重新切批的每一批文件清单」改为对照开跑时冻结的完整批次计划(issue #253):`review_run` 多一列计划 JSON(全部批次的文件清单,按批次序号排),开跑时与历史快照同一次写下,之后不改;续跑时重新切批的每一批都要与它逐字相同,已完成与未完成的批次都在核对之内。原口径只核对已落库的批次,看不出「总批数相同、已完成的首批相同、未完成部分的分组变了」——用基线 7c558f8 的切批函数验证过的反例:六个文件的改动行数依次 10、10、95、10、10、10,上限 999 行 / 2 文件切成「ab、cd、ef」,改成 100 行 / 3 文件切成「ab、c、def」;那时剩余文件的并集不变,变的是分组与按文件路由的知识条目和历史注入,续跑会把改变后的分组混进原轮次。现实触发条件是停机期间管理员改了分批上限,或升级改了缺省值且该项未设。计划在开跑时写一次,与本决策否决的「整轮 JSON 每批覆盖」不同:它不承载中间态,批次结果仍按批次一行各写各的。没有计划的升级前轮次读回即「不可续跑」,与没有历史快照同律,一律退回改判;已完成的历史轮次只多一列 NULL。恢复粒度、已完成批次复用、排空停在批次之间、中间态独立于事后统计这些约定都不变。

## 修订(2026-09-21)

恢复粒度从「批次」细化到「**Reviewer × 批次**」(issue #410)。原口径要整批全部 Reviewer 都跑完才落库,而批内先完成与后完成的模型差得远:线上 DEV/AI-API 的定时完整审查实测(Run #118、#112)一批平均 725–751 秒,批内先后相差 310–541 秒。进程在这段窗口里停下时(排空上限 300 秒小于批次时长,发版撞上轮次就会;OOM 与宿主机掉电同理),已经跑完的那个模型的结果只在内存里,续跑整批重跑——opus 每批约 10M token,并发 3 批时一次最多白花约 30M;它同时让 issue #408 的批次收尾事件在同一批上出现两条。

改法:每个 Reviewer 在一批上的结论拿到手、批外过滤做完,当场写进中间态表;续跑时一批里库里已有结果的 Reviewer 直接取那一份、不再调用,只跑缺结果的那几个。中间态表因此从「一行一批」改成「一行一个(批次, 模型)」,主键加上模型,那一批的文件清单不再随行存——冻结的批次计划已经逐批写着它,而没有计划的轮次本来就不续跑。升级前的整批行按模型拆开后删旧表:旧行只在整批全部模型跑完之后才写,拆开因此无损,那一批照常整批跳过。

**本决策的核心前提不变**:批内的 Pi 会话在内存里、中途续不了,恢复单位仍是一次完整的 Reviewer 会话,只是不再要求同批的其他 Reviewer 陪它一起重跑。冻结的批次计划与历史快照、续跑的核对项(head、知识集版本、最低报告等级、批次分组、模型组合)、续跑不成立时退回改判失败、收尾只做一次、「一轮只发一次 review」、排空停在批次边界、中间态不进任何事后统计的分母、轮次正常结束后中间态的清理,全部照旧。

落库排在这个模型这一批的收尾事件之前:两者之间进程停下时,先落库丢的是轨迹上的一行(那一批的收尾事件缺席),先发事件丢的是结果——续跑会重跑这个模型,同一个(模型, 批)上因此出现两条收尾,而这一趟模型调用白花。保住已花的 token 是本次修订的目的,轨迹少一行是可接受的代价。

## 修订(2026-09-21,issue #415、#422)

「续跑那一轮的耗时只算续跑这一段」作废,**单模型与轮次级从此是同一条规则**:耗时取各批时间区间的并集。崩溃前已落库的那几批带着自己的开始时刻与耗时,它们跑掉的时间因此保得住;两次进程之间的停机没有区间盖着、自然不计;批次并行下重叠的那段仍只算一次。轮次级那一份是「续跑这一段 + 崩溃前各批的并集」——崩溃前的那几批与续跑这一段之间隔着停机,两者相加与整份取并集是同一个数;只取开始时刻早于本进程这一段的那些区间,连续续跑两次时前两个进程的区间都在库里,同一条规则覆盖。并集的实现只有一份(`batch.ts` 的 `spanUnionMs`),两处调它。

#415 先只改了单模型那一侧,续跑轮次上因此会出现轮次耗时小于其中某个模型的耗时,面板上两个数看着矛盾;#422 把轮次级一并改过来。崩溃前的准备阶段(备工作副本、读历史)没有记录,两侧都不计。没续跑的轮次逐数不变:崩溃前的区间是空的。
