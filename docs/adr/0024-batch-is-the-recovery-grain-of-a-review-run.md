# 批次是 Review Run 的恢复粒度,中间态与统计分开存

一轮 Review Run 被服务重启打断时,各批的结果只在内存里等全部批次跑完才随收尾事务一并写库。进程落地(发版、容器重建)就把已经跑完的批次成果全部丢掉,已经花掉的 token 保不住,重跑只能从头开始。issue #247 把这些轮次改判失败,止住了「永远显示进行中」;本决策定的是它前面那一步——先尝试续跑。

选定的做法:**批次是恢复粒度**。每一批跑完立即把该批各 Reviewer 的结果写进一张只服务「还没收尾的那一轮」的中间态表 `review_run_batch`(键是 `run_id + batch_index`,存这一批的文件清单与各 Reviewer 的结果 JSON);开跑时把本轮用到的历史 Finding 快照写进 `review_run.history_json`。服务启动时对没有结束时间的轮次重新准备工作副本、按同一 head 重新切批,只跑库里缺结果的批次,再走现有的合并、收尾与发评论。收尾仍只做一次,一轮只发一次 review 不变;`finishRun` 在同一个事务里把该轮的中间态行删掉。

恢复粒度取批次而不是更细:Reviewer 的 Pi 会话用 `SessionManager.inMemory()`(ADR 0017),批次跑到一半的会话随进程消失,续不了。

## Considered Options

- **每批的结果直接写进 `reviewer_outcome` 与 `finding`。**这两张表是事后统计的来源:处置率、模型参与度、用量都从它们算。中间态混进去,一轮跑到一半的结果就进了分母,而合并、跨轮匹配与自动处置都还没做——那些行既不是最终的 Finding Identity,也没有 resolve 载体。要把它们排除就得给每一行加「这一轮结束没有」的判据,每一处统计各自记得带上它。
- **快照历史不落库,续跑时重读当前历史。**重启期间有人处置了一条历史,续跑的批次拿到的历史就与原轮各批不同:同一轮里前几批被要求复核的条目,后几批看不见了。一轮的注入必须是同一份。
- **把整轮的中间态写成一个 JSON 大对象,每批覆盖一次。**批次受限并行(issue #232)下几批同时结束,读改写会互相覆盖。按批次一行则各写各的,并发天然安全。
- **续跑不核对冻结前提,直接接着跑。**head 变了、分批上限改了、知识集版本推进了、模型组合换了,已落库的批次与新切出的批次就指向不同的文件集或不同的规则,合出来的覆盖是错的。

## Consequences

- 库里多一张中间态表。它只在「开跑到收尾之间」有行:收尾与改判失败都会把该轮的行删掉,长期占用因此不随轮次数增长。
- `review_run` 多一列历史快照。它随轮次永久保留——回看一轮时「当时注入的是哪些历史」从此答得出来。
- 续跑的前提在 `runReview` 里当场核对(head、知识集版本、重新切批的每一批文件清单、Reviewer 组合),任一条不成立即抛,由启动侧退回 issue #247 的改判并写上原因。**续跑不成立是常态之一,不是异常**:管理员在重启期间改了分批上限或知识集,那一轮就该从头重跑。
- 升级前落库的轮次没有历史快照,读回即「不可续跑」,一律退回改判。
- 续跑那一轮的耗时只算续跑这一段:崩溃前跑了多久、进程停机多久都没人知道,拿结束时间减开跑时间会把停机时长也算成审查耗时。
- 启动时逐轮串行续跑:同时续跑几轮会一次开满「批数 × 模型数」个子进程,与批次受限并行防的是同一件事。没有中断轮次时启动路径零改动。
