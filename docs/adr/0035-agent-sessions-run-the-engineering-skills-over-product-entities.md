# Agent 会话跑作者的工程 skill,仓库文件与 issue tracker 由产品实体替代

spec #342 把产品知识定成「一句说到两个以上仓库的陈述」,由系统自跑的梳理会话一次交卷、人逐条确认。线上唯一真实产品跑出来的 21 条全是接口契约,没有一条说这个产品是做什么的;100 字硬顶、逐条独立、无子代理、无人对答四个约束把深度锁死,而 Review Run 不读它,产出也没有消费者。需求拆分同样是无访谈纪律的一次产出,拆分条目定稿后无处可去。作者在本仓库上已经有一套解决这两件事的纪律——grilling、domain-modeling、to-spec、to-tickets,由 ask-matt 路由——它们假定有仓库文件可写、有 issue tracker 可发。选定的做法(spec #357):**这套 skill 原样 vendor 进镜像、按用途铺进会话 agentDir 的 `skills/`;skill 期望的三样东西由产品实体替代:CONTEXT.md 与 docs/adr 换成产品知识(术语表、仓库关系、决策记录),issue tracker 换成产品 tracker(spec 与票),triage 标签固定五个值;提示里只加一段替代说明。**人在提问轮次的选择卡片上答题,答即裁决,产出即刻生效;Reviewer 与全部会话用途的提示带三行目录,正文经 `query_knowledge` 按需读。ADR 0032 里「产品知识是自己的实体、挂在产品上」仍成立,「产品知识不进 Review Run」由本决策取代。

## Considered Options

- **改提示词、放宽字数、加子代理,实体不动。** 只会得到更长的同类句子:定义把业务层排除在外,逐条独立的一句话装不下流程与理由。
- **五章固定目录的产品文档,agent 自主深读后一次交卷,人按章裁决。** 覆盖得了业务层,但仍是 agent 单方面理解后交人核对;34 条提案零裁决已经证明「读完再核」没人做得动。访谈把核对拆进每一轮回答里。
- **把 skill 的规则转写进系统提示,不 vendor 文件。** 提示自持,但与上游 skill 演进脱钩,每次上游改纪律都要人肉同步;原样铺进 agentDir 只需一段替代说明,升级 skill 即升级镜像。
- **产物写进仓库文件、spec 与票发到 Gitea issue。** 与 skill 原始形态一致,但产品跨三仓、消费者是 Reviewer 与会话,都经库读;Gitea 1.26 的 issue API 能承接依赖边却没有 sub-issue,frontier 要 N+1 查;作者明确票以后在本平台消费。存库、产品页展示,导出 Markdown 留给人。

## Consequences

- 提案队列、驳回记忆与手写条目取消:`product_knowledge` 与 `product_knowledge_rejection` 删除重建,存量丢弃(线上无一条已裁决)。需求拆分的产出表、定稿表与产出栏退役,行丢弃,会话记录保留可读。
- 梳理会话只由人开,仓库集变动不再触发;同一产品同时只有一场未完成的梳理。
- 术语定义不含实现细节,出处附注另存、只在产品页展示、不进提示。
- ADR 只在难逆、无上下文会惊讶、真实权衡三条件同时成立时由 agent 提候选,人确认才写。
- Reviewer 多一个 `query_knowledge`,不设每批调用上限;仓库规则与事实的注入方式不变。
- 提问轮次与会话子代理是通用会话能力,所有用途可用。
- 需要写文件、跑 git 或 shell 的 skill(prototype、tdd、implement、research、wizard 等)不铺进会话;会话工具面仍只读加产品实体的写工具。
- 票在本平台上的消费(实现用途)是下一份 spec;本决策只让票存在并可读。
