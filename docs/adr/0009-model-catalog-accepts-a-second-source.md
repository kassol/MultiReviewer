# 模型目录允许第二个来源:厂商目录

模型目录此前只有两层:Pi 内置表,加上 pi.dev 的**远程目录**。两层都由 Pi 一家供给,缺什么就得等上游补。实测 OpenRouter 现货 414 个,内置加远程只有 348 个:差出来的 67 个在官网上看得到,选择器里搜不到,而它们并没有任何毛病。

于是给目录开第二个来源:**厂商目录**——某一家模型厂商自己公布的模型清单。读目录时在远程目录之后再拉一次,把两层都还没有的模型补进去。这轮只接 OpenRouter,判据在 `docs/research/vendor-model-catalog-apis.md`:13 家实测里只有它免鉴权就给全量,而且响应自带单价与上下文窗口。

开第二个来源就要说清它与已有那两层的关系。两条约束把它钉死:

- **已有行不动,只补缺。**按裸 model id(模型标识 `provider:model` 的后半段)对齐,撞上的一行整行保留,不论它来自内置表还是远程目录。Pi 独有的 `openrouter:auto` 因此留得下来,已经在模型组合里的那些标识一个都不用重选。**「已有」不含这一层自己上一轮补的那批**:那批每轮按当下的清单重算,见下面「下线的模型自己消失」。
- **补进来的行必须进共用落盘。**写进远程目录那一份 `models-store.json`,与远程目录的行同一条通路。面板选得出的模型,不联网的 Reviewer 子进程必须取得到——只补进面板进程内存的话,操作员选完会在 Review Run 里撞上「模型不存在」。

## Considered Options

- **等 pi.dev 补齐。**不加代码,但补不补、什么时候补都不由本项目决定,而缺的那 67 个此刻就在官网上挂着。
- **在本仓库维护一张模型表。**目录随厂商每周变,手抄的表过期时表现为「官网有、面板没有」,与今天这个问题一模一样,只是多了一份要人维护的文件。
- **只靠手填模型标识兜底。**手填是另一条入口,一次一个;它解决的是「一手厂商的清单本来就拿不到」,替不了一次补齐 67 个。两条入口并存。
- **先做一层厂商目录注册表,把 38 家都容纳进来。**只有一个实现的抽象没有第二个实现来校验形状,而下一家的形状恰恰还不知道(要 key、缺单价,两件事都还没有答案)。这里只留一个接口、一个实现。

## Consequences

- **目录加载多一步,不多一条缝。**厂商目录是 `loadFromPi` 里远程目录之后的一步,不是新端点、不是新设置页、不新开 HTTP 客户端、不新加配置项。超时上限与进程内缓存都沿用目录加载那一套,一个进程付一次。
- **两层的成败各记各的。**远程目录拉不到不妨碍问厂商目录,反过来也一样。目录端点在 `remote` 之外多一个 `vendors`,按 provider 报 `ok` / `unavailable` / `off`:少模型时运维要能分清是哪一层没生效。面板这轮不画这个字段。
- **`PI_OFFLINE` 一次关两层。**沿用 Pi 自己的开关,不加项目自己的变量。关掉时厂商请求一个都不发,选择器只剩内置那一份。
- **拉不到就降级,不失败。**HTTP 非 2xx、超时、响应不像目录都算没拉到,目录照常给出内置加远程那一份。选择器空白比少几十个模型严重得多。
- **补进来的行按落盘那一份的形状写全。**`api` 为 `openai-completions`、`baseUrl` 为 OpenRouter 的 v1、`provider` 为 `openrouter`,单价从官网的「每 token 多少美元」换成落盘用的每百万 token(差这个 10^6 的话,那一行跑出来的 Review Run 成本会小六个数量级)。`compat` 不写:pi-ai 在模型没写这一项时按 provider 与 baseUrl 自己推,推出来的正是远程目录那些行里写着的值,抄一份只会把上游的判断冻在落盘里。
- **共用落盘拿不到时不补。**缓存目录建不出来的那一档(两侧退回私有临时目录),厂商目录整层报 `unavailable` 而不是补进内存:那时候补了也只是造出一批子进程取不到的模型,正是本条约束反过来的样子。
- **下线的模型自己消失,不等远程那一层。**厂商目录这一层落进 `models-store.json` 的那批行,每次读目录都按当下拉到的清单整批换掉上一轮那批,认上一轮那批靠该家条目上多出来的 `multireviewerVendorModels`(Pi 只认 `models` / `checkedAt` / `lastModified` / `etag`,多出来的键它原样带着走)。厂商下线一个模型时那一行因此跟着消失,同一个 id 在落盘里也只出现一次。

  判据来自读 Pi 源码加临时脚本实证(`dist/core/remote-catalog-provider.js` 与 `dist/core/models-store.js`,0.84.0):远程目录拉到 200 时 Pi 确实把该家条目整条换成一个只含远程行的新对象(`publish({ persist: entry })`),我们那一层的行与记号一起被冲掉,下一次读目录按当下的厂商清单重新补。**但那一刻不由本项目决定,而且经常不来。**三条实测:

  - **4 小时刷新窗内不重拉,落盘那一条一动不动**(`REMOTE_CATALOG_REFRESH_INTERVAL_MS`,判据是 `checkedAt`,而我们写落盘时保留它)。同一份落盘连读三次目录,已下线的那一行三次都还在。
  - **pi.dev 那一家持续拉不到时永远不动。**非 2xx 那条路写回的是 `{...stored, checkedAt}`——`models` 原样留着,而 `checkedAt` 还跟着往前推,于是下一个刷新窗重新开始。
  - **pi.dev 回 404 / 501 时那些行变成只在文件里的死行。**Pi 把 `lastModified` 压成 0,而它判过期看的正是这一位与内置表生成时间的先后,于是那些行再也不恢复进内存;运行时看不见它们,盲追加就会每读一次目录再把整批追加一遍,文件单调增长。Pi 升级后内置表的生成时间新过落盘的 `lastModified` 时是同一档。
- **这一层的写入让目录加载变成串行的。**往共用落盘写是「整份读进来、改一家、整份写回去」,两份加载同时在飞时后写的会把先写的整批账抹掉,而 Pi 给这份文件用的那把锁拿不到(受锁存储只在 `dist/core/models-store.js` 里导出,包的 `exports` 映射不开这个入口;`proper-lockfile` 只是 Pi 的传递依赖,运行时第三方依赖有意只有 Pi 一个)。因此把 `loadFromPi` 排在一条模块级 promise 链上,同一时刻只有一份在跑:真实的重叠窗口只有「一次读还在飞时有人失效了缓存」这一个,串起来就把边界设计掉了。它依赖「这份落盘只有服务进程写,Reviewer 子进程只读」这个前提。
- **接第二家之前先解决两件事。**目录加载怎么拿到凭据(现在它不读凭据表,读了就等于「还没配凭据也能看见完整目录」失效),以及缺单价的行成本怎么算。顺序是 Together → Groq → Anthropic。
