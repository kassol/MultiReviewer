# 延续的交接在新评论发布确认后完成

ADR 0016 定了延续:复核仍在而指纹已变时,新位置的评论承接同一条 Finding Identity,旧评论 resolve 并记「已延续」。基线 7c558f8 的实现顺序是先 resolve 旧评论,再落库轮次与延续,最后发布新评论(issue #252 复现);理由是新评论正文里「延续自」那句要等 resolve 成功才算真。发布失败时旧 Finding 已记「已延续」、新 Finding 没有评论载体、轮次已结束且不算失败——一条未处置的问题从此在 Forge 上没有可处置的载体,启动续跑也不会再选中它。

选定的做法:**交接以新评论的载体确认为准**。顺序改为发布 review 并读回评论标识 → resolve 旧评论 → 落库延续。「延续自」那句保留在新评论正文里:延续关系在发布之前已由本地判定(词法配对、复核结论自带位置、合并 agent 命中三档之一),这句话描述的是谱系,旧评论关闭只是交接的收尾动作。

三种失败各有归宿:

- **发布明确失败**(Gitea 回错、review 未创建):不 resolve、不记延续,旧行留在未处置,本轮审查结果照常落库,轮次记失败原因(ADR 0026)。
- **发布成功而 resolve 旧评论失败**:仍记延续,延续带「交接未完成」;旧评论留在 Forge 上可处置,面板把旧行标为待关闭。下一轮 Review Run 收尾时重试 resolve;回填读到旧评论已被 resolve 也算交接完成。
- **发布结果不确定**(review 已创建但读回评论失败,或无法判定是否已创建):按发布失败处理,但禁止自动重发;已取得的 review id 随失败原因保存供人核对,启动续跑不再自动发布这一轮。

## Considered Options

- **保持先 resolve,发布失败后 unresolve 补偿。**补偿走同一条网络,失败概率与主动作同级;补偿再失败时旧评论已关、本地却没记延续,状态比现在更难解释。
- **发布优先,resolve 失败降级为普通新 Finding。**新评论正文已经写了「延续自」,降级后这句话是假的;同一处问题在 Forge 上留两条打开的评论、本地却当两条 Identity,处置率重复计。
- **正文不写「延续自」,只靠本地 `continued_from`。**读 Forge 的人失去谱系线索,与 ADR 0016「新评论正文注明延续自哪条旧评论」相悖。

## Consequences

- `applyContinuations` 移到发布之后执行;延续落库多一格交接状态。
- 「已延续」的语义不变:旧行的处置值仍是 `continued`,交接未完成只是它上面的一个待办标记,不计入处置率。
- 轨迹的 `finding_continued` 事件带交接结果;面板在旧行与轮次详情上呈现「交接未完成」。
- Gitea adapter 的发布要区分「创建未成」与「创建后读回失败」,后者把 review id 带在错误里。
- PR 触发与范围审查、完整审查与只复核、三档延续判据共用这一套顺序;回填对 `continued` 行的「两个方向都不覆盖」只放开一格:读到旧评论已 resolve 时把交接标记为完成。
