# Finding Identity 是同一处的同一问题,跨轮次折叠由合并 agent 判定,同根因组与合并组分层

ADR 0015 把 Finding Identity 定为「同一 pull request 里指向同一处未改动代码的 Finding」,ADR 0022 让合并 agent 判「是不是同一个问题」但只在本轮之内,跨轮次仍是指纹命中优先。AI-API 范围审查 #11 的审计(2026-09-04)与综合说明验收(2026-09-07)把两条前提都推翻了:

- 同一行代码上两个模型报出两个不同的问题(比如一个空指针、一个泄露密钥),本轮内合并 agent 能拆开,可只要其中一条上一轮报过,这一轮的另一条就被指纹命中直接并进旧条——旧条若已驳回,新问题连评论都不发。「同一处」在这里把两个问题压成了一个。
- 同一个写坏的函数在 23 个文件里各被报一次,系统里是 23 条互不相干的 Finding,人要逐条看、逐条处置。去重机制只看同文件同位置,看不见「这是一回事」。

因此两条决定:

**Finding Identity 是「同一处的同一问题」。**「同一处」仍由代码定(文件 + 内容指纹,±3 行容差),「同一问题」由合并 agent 判,同一轮内与跨轮次一个口径:指纹命中的历史 Finding 交给合并 agent,它归为同一组才折叠,没归即同一处的新 Finding,正常发评论、进阶段统计,不继承旧条的处置。合并 agent 不可用的那一轮退回「同一处即同一条」的指纹折叠,最坏情况恒等于此前的行为。

**同根因组是合并组之上的另一层。**合并组回答「这几条是不是同一处的同一问题,该合成一条」;同根因组回答「这几条各自成立,但出自同一个根因」。合并 agent 在同一次调用里,归组完成后顺带提出同根因组:成员来自至少两个合并组,不限文件,组附一句根因说明。组内每条 Finding 仍独立——Identity、正文、评论、处置都不因入组而变;组只提供面板上的按组展示、对未处置成员一次写同一处置的入口,以及 Forge 评论末尾一行指向其余各处。组每轮重新提,成员含本轮折叠或延续到的历史 Finding,不跨轮次保持同一性。

同一批决定:范围审查分批审查时,Reviewer 只报本批文件,批外文件的报出在编排层丢弃并记一条审查轨迹,不落库。批外报出的落点质量通常更差,而每个文件都恰好在一个批里被审到,丢弃不损失检出。

## Considered Options

- **保持指纹优先,只让本轮内 agent 拆分。**代价是跨轮的同处新问题永远并不出来,越是被驳回过的位置越容易压掉新问题。指纹是「同一处」的硬证据,但「同一处」从来不等于「同一问题」,把两者等同是 0015 时代样本不足下的简化。
- **同根因组合成一条多锚点 Finding。**一条 Finding 带 N 个位置,Forge 评论按位置各发。Finding 模型、六处锚点逻辑、延续与复核都要按多位置重写,而作者真正需要的只是「知道这是一件事、能一次处置」。
- **同根因组由独立 agent 一步提出。**职责单一,但多一次模型调用与一套失败面,而合并 agent 此刻已经拿着全轮所有 Finding 和读代码工具,正是判断根因的最好时机。
- **同根因组阶段级持久、跨轮并入。**组有自己的 id,agent 每轮看到已有组并并入。多一层跨轮匹配与失效处理,而组的用途(看清一件事、一次处置)在一轮之内就完成了。
- **跨批报出保留、交给合并 agent 归组。**能留住批外的检出,但批外报出没有那个文件的 diff 作依据,落点差;每个文件都会在自己的批里被审,保留只带来重复。

## Consequences

- CONTEXT.md「Finding Identity」词条改口,新增「同根因组」词条;ADR 0015 与 0022 加附记指向本 ADR。
- 阶段汇总按 Identity 计数的地方要允许同一「文件 + 指纹」下有多条 Identity;「参与条数」与处置率口径不变。
- 合并 agent 的方案多一层输出(同根因组)与一条硬性质:组成员必须来自本轮至少两个不同合并组,违反即丢弃该组,不作废整份分组方案。
- 已处置历史上的同处新问题从此会发出评论。若某处代码本身就是「不用报」的场景,该走评审规则(对评审的限定)压掉,而非指望位置上的旧驳回。
- 存量 Finding 不回溯:历史上被指纹压成一条的不拆,已有的 46 簇重复按作者既定做法人工处置。
