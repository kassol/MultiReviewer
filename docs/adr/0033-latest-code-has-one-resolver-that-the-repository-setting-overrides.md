# 「最新代码」只有一个解析处,仓库的默认分支设置覆盖它

拿不到基准的 agent 流程读的是「这个仓库最新的代码」:系统开的产品梳理、无锚点的人工提议与修订意图,以及 Agent 会话的工作树。它们此前共用一处读法——`src/git/worktree.ts` 的 `defaultBranchHead`,它取 Gitea 报的默认分支当前 head。开发、预发与生产线都不在 Gitea 默认分支上的仓库,这些流程因此读的是没人开发的那份代码,提案与拆分都从旧代码推出来。

选定的做法:**仓库注册表上加一处可空的默认分支设置,`defaultBranchHead` 成为「生效的默认分支 head」的唯一解析处**——设了就用设的那条,没设即 Gitea 的默认分支。全部「读最新代码」的调用方都经它,不各自取;设的那条分支在远端已经没有了就抛出带仓库名与分支名的错误,不静默回落到 Gitea 那一条。commit 选择器不认识这个设置:分支列表端点把生效的默认分支标成默认,选择器因此开在同一条分支上。基点探索这类人自己选 commit 的流程不受影响——它们的基准来自人的输入。

## Considered Options

- **每个流程各读一次设置。**产品梳理、人工提议与会话各自「有设置用设置、没有用 Gitea」。三份判据迟早漂:新流程接进来时最容易漏掉这一半,而漏掉的表现是「读了别的分支的代码」,没人看得出来。
- **改 Gitea 上的默认分支。**不写一行代码就能解决,但 Gitea 的默认分支决定 pull request 的默认 base 与仓库首页,团队按它协作;为了让 agent 读对代码去改它,是拿协作约定换一个工具的读法。
- **分支不存在时回落到 Gitea 默认分支。**流程不会失败,代价是人设过的意图被静默换掉:提案说的是另一条线上的代码,而没有任何地方说出这一点。失败一次比读错一次便宜。
- **每个仓库可设多条(开发 / 预发 / 生产)。**需求里提到三条线,但拿不到基准的流程每次只需要一条;哪一条由人在设置里定,多条就要再定「哪个流程用哪条」,而那正是这一票要消掉的分叉。

## Consequences

- CONTEXT.md 新增「默认分支」词条;它是仓库设置的一格,与模型覆盖、辅助模型、最低报告等级同在仓库配置弹窗与 `PUT /repos/{id}/settings` 的整页替换里,同一个版本号。
- 保存时对照这个仓库此刻的分支列表校验,远端没有的那条整次不写;分支列表端点因此多给 `repo:write` 一格读权限。
- `defaultBranchHead` 每次先同步一次远端:它要的是这条分支此刻的 head,而本地副本里的远端分支可能是上一次准备时的快照——那样既读不到刚推上去的提交,也看不出这条分支已经被删掉。
- Review Run、每日增量与范围审查不受影响:它们各自带 base 与比较项。Finding 锚定的处置反哺仍停在那条 Finding 报出时的 head。
- 人自己发起的产品级流程(重梳、建会话)在发起时逐仓库选 commit(issue #352、#353);没选的仓库仍落到这一处解析。
