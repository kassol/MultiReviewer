# 审查轨迹以自定义事件行落库,不保留 Pi 的会话文件

Reviewer 跑在子进程里,Pi 的会话用 `SessionManager.inMemory()`,过程只在内存里存在;编排层只数 `report_finding` 被拒的次数,其余事件全部丢弃。面板因此只能看到「进行中」与最终的 Finding,一个报得少或报得歪的 Reviewer 读了什么、怎么推理的,事后无从查起。线上使用(2026-08-25)把这件事提成需求:运行中能实时看到每个 Reviewer 的过程,结束后能回看。

Pi 自带的持久化是会话文件(jsonl,`SessionManager.create()` 落盘),被评估并否决。选定的做法是:子进程订阅 Pi 的会话事件,经既有的 IPC 通道逐条转发给编排层,编排层把它们与自己的编排事件一起写成 SQLite 里的事件行,一行一个事件,按轮次内的序号排列;面板打开时读表补历史,运行中经 SSE 推送新增的行。事件的正文是完整的,不设截断上限;工具返回的内容只记长度,不记正文。

## Considered Options

- **Pi 写会话文件,库里存路径。**会话文件是 Pi 的私有格式:条目类型随 Pi 版本变化,含 compaction 与分支树等与审查无关的结构,工具返回的源码全文也在里面。它只覆盖模型对话,批次起止、Finding 合并、评论已发这些编排事件不在其中;且它在消息完成时才追加,做不了实时。面板还要多维护一份对 Pi 格式的解析。
- **事件行与会话文件都留。**多一套文件的生命周期要管,而会话文件能回答的问题事件行都能回答。
- **只推送不落库。**跑完即丢,事后回看这个主要用途不成立;断线续传也需要序号来源。

## Consequences

- 库里多一张按 Review Run 归属的事件表,随 Review Run 永久保留;Review Run 没有删除路径,轨迹也没有。
- 子进程与编排层之间的 IPC 协议从「只回传 Finding」扩成「回传事件流」;子进程崩溃前已转发的事件自然保留,失败原因作为最后一条事件补上,stderr 仍走服务日志。
- 事件的形状由本项目定义,Pi 升级只影响子进程里的订阅代码,不影响表与面板。
- 面板与后端之间多一个 SSE 端点;它沿用轮次详情的权限,能看轮次就能看轨迹。
- assistant 文本按整条消息记,不记流式增量,实时推送与落库是同一份事件。
