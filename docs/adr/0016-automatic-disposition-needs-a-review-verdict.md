# 自动处置以 Reviewer 的复核结论为证据

ADR 0013 把「指纹在新比较项上算不出且本轮未再报出」当作代码已改动的证据,自动 resolve 并记「已改动」。它依赖 Reviewer 对历史一无所知——只有这样「未再报出」才是模型独立作出的判断。线上验证(2026-08-25)显示这条证据太弱:模型一轮报三条、下一轮报零条,同一处未修的问题只因指纹未变才没被误标;而作者常见的「在上游加判空」这类修法指纹不变,永远进不了自动处置。同一审查阶段内的后续轮次本来就该知道历史,否则重复报出与漏报都无法由平台约束。因此:每轮 Review Run 把本审查阶段全部历史 Finding 注入 Reviewer(未处置的给全文与处置备注,已处置的给文件行、标题、状态与备注;不给操作人,不设条数上限),Reviewer 对每条未处置的历史 Finding 显式复核——仍在 / 已修 / 无法判断。自动处置以「已修」为唯一证据,处置值记为「已修复」;指纹只做辅助信号,不再单独构成证据。多个 Reviewer 结论冲突时仍在优先,全部已修才自动处置;漏给结论按无法判断计,不动。复核仍在而指纹已变时,新位置的评论承接同一条 Finding Identity,旧评论 resolve 并记「已延续」,不计入处置率,新评论正文注明延续自哪条旧评论。人已作出的处置一律不被自动处置覆盖;人把「已修复」改回未处置后它就是人工处置,自动规则不再碰。PR 触发与范围审查同一套规则。

## Considered Options

- **只注入历史,规则不动。**注入后「未再报出」成为常态,这条证据自动失效,除非 prompt 要求模型把未修的历史问题再报一遍——那等于用更绕的方式要一个复核结论。
- **复核「已修」与指纹消失双条件。**最保守,但把上游修法排除在外,而那正是 0013 的规则认不出、本 ADR 要解决的情形。
- **任一 Reviewer 判已修即自动处置。**误判成本落在人身上,且与「仍在优先」的保守取向矛盾。

## Consequences

- 本 ADR 取代 ADR 0013。「已改动」这个处置值由「已修复」取代,含义从「代码变了」改为「模型复核判定已修」。
- Reviewer 契约多一个复核动作,每轮的输入随阶段历史线性增长;已处置条目只给一行是唯一的体积控制。
- 处置备注进入 Reviewer 的输入,但仍只存面板、不写 Forge(CONTEXT.md 处置备注)。
- 「已延续」写回 Forge 的仍是 resolve;Forge 上分不出已修复、已延续与人工处置,区别只在本地库与面板。
- 所有 Reviewer 都失败的那一轮不做任何自动处置:没有复核结论就没有证据。
