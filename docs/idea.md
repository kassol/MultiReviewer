**类似产品产品与架构文档（简化版）**  
**定位**：构建一个多模型并行、基于真实 Coding Agent 的 GitHub PR 智能审查工具（参考 Code Terrier 的核心思路，但独立设计）。

**文档目标**：给出可落地的产品定义 + 高层架构，并明确标注当前不确定、需要进一步探讨的设计点。

### 1. 产品概述

**产品名称**（示例）：MultiReviewer / CodeGuard / ParallelReviewer（可自定）

**一句话定位**：  
通过真实 Coding Agent（可打开文件、探索上下文）+ 多模型并行审查 + 交叉验证，为 GitHub Pull Request 提供低误报、可收敛的智能代码审查。

**核心价值**：
- 解决单模型审查盲点与高误报问题
- 解决纯 diff 扫描上下文不足问题
- 解决 AI Review 容易无限发散、无法收敛的问题
- 适配“vibe coding / AI 生成代码”场景，降低累积技术债

**目标用户**：
- 个人开发者 / 小团队（高频使用 AI 写代码）
- 希望在 PR 阶段尽早拦截 bug / 安全问题的团队

**核心差异化**：
- 不是“再加一个 LLM 评论机器人”
- 而是「Agent 驱动 + 多模型交叉验证 + 增量可收敛」

### 2. 核心功能（建议实现）

| 功能模块 | 描述 | 优先级 |
|---------|------|--------|
| 自动/手动触发 | PR 创建、新 commit 自动审查；支持评论 `@xxx review` 手动触发 | P0 |
| 多模型并行审查 | 同时调度 2~3 个不同模型（可配置） | P0 |
| 真实 Agent 审查 | 使用 Coding Agent（如基于 Pi 或自研）打开文件、跟随变更、探索相关代码 | P0 |
| 交叉验证 | 一个模型提出的 finding，由其他模型进行 grading / 确认，降低误报 | P0 |
| 增量与收敛 | 基于 diff 做增量审查；支持回复评论后 re-check，并标记已解决项 | P0 |
| Inline 输出 | 精确到行的 GitHub Suggestions + 分类（Security / Bug / Flag 等） | P0 |
| 密钥灵活 | 支持用户自带 Key（BYOK）或平台共享池 | P1 |
| 非阻塞 Status | 设置 commit status，但不强制阻断合并 | P1 |

### 3. 高层架构

```
┌─────────────────────────────────────────────────────────────┐
│                        GitHub                                │
│          PR Events / Comments / Diff / Files                 │
└──────────────────────────┬──────────────────────────────────┘
                           │ Webhook + GitHub API
                           ▼
┌─────────────────────────────────────────────────────────────┐
│                   后端编排服务 (Orchestrator)                 │
│  ┌─────────────┐   ┌──────────────┐   ┌──────────────────┐  │
│  │ 事件接收     │→  │ 任务调度与    │→  │ 结果聚合 /       │  │
│  │ + 权限校验   │   │ 并行控制      │   │ 交叉验证 / 过滤  │  │
│  └─────────────┘   └──────┬───────┘   └────────┬─────────┘  │
│                           │                    │            │
│                           ▼                    │            │
│               ┌────────────────────────┐       │            │
│               │  Coding Agent Runtime  │       │            │
│               │  (Pi / 自研 / 其他)     │ × N   │            │
│               │  每个绑定一个模型       │       │            │
│               └────────────────────────┘       │            │
│                           │                    │            │
│                           ▼                    ▼            │
│               LLM Providers (用户 Key / 共享池)             │
└───────────────────────────┬────────────────────────────────┘
                            │
                            ▼
                   GitHub Inline Comments
                   + Commit Status
```

**主要组件职责**：
- **事件与接入层**：接收 Webhook，拉取 PR diff、相关文件、历史评论。
- **编排层**：决定启动几个 Agent、分配哪些模型、控制并发与超时。
- **Agent Runtime**：真正执行审查（读文件、探索代码、生成 findings）。
- **验证与聚合层**：去重、跨模型 grading、行合法性检查、过滤。
- **输出层**：发布 Suggestions 和 Status。

### 4. 核心工作流

1. 触发（自动 / 手动）
2. 拉取上下文（diff + 必要文件 + 历史人类评论）
3. 并行启动 N 个 Agent（每个绑定不同模型）
4. 各 Agent 独立产出 findings
5. 聚合 → 近重复合并 → 跨模型验证 → 过滤
6. 发布结果
7. 新 commit 或回复评论时进入增量 / re-check 循环

### 5. 关键设计决策与探讨空间（重点）

以下是实现类似产品时最需要提前讨论和验证的点：

**5.1 Agent 选择与封装**
- 直接基于现有开源 harness（如 Pi）二次开发，还是自研轻量 Agent Runtime？
- Agent 需要哪些最小工具集？（read / grep / list_dir 是否足够？是否需要 bash？）
- 如何保证 Agent 不会对仓库产生副作用（只读模式强制）？

**5.2 交叉验证机制（最核心差异点）**
- 验证是简单的“同意/不同意”，还是打分 + 理由？
- 模型之间意见不一致时，是丢弃、降权，还是需要第三模型仲裁？
- 如何平衡“降低误报”与“不漏报真实问题”？

**5.3 增量审查与收敛策略**
- 新 commit 时只审查 diff，还是 diff + 相关上下文？
- 历史 findings 如何跟踪状态（已解决 / 仍存在 / 新增）？
- 如何防止 AI Review 无限发散？是否需要“本轮最多新增 X 个 finding”或“已解决项不再重复报”的硬规则？

**5.4 上下文管理**
- 大 PR / monorepo 场景下，如何控制 token 消耗与上下文质量？
- 人类评论作为上下文时，是否需要标注“untrusted”并限制权重？

**5.5 模型与成本控制**
- 默认用哪些模型组合效果最好？（强模型 + 便宜模型搭配？）
- 用户自带 Key vs 共享池的成本与隐私权衡
- 是否需要按仓库 / 用户做 token 配额与优先级队列？

**5.6 工程与安全**
- Agent 执行环境是否需要沙箱？
- GitHub App 最小权限集是什么？
- 审查结果是否需要留存？留存多久？

**5.7 产品化细节**
- 免费版与付费版如何切分（模型数量、并发、优先级、历史记录等）？
- 是否支持自定义审查规则 / 忽略列表 / 项目级配置？

### 6. 建议落地路径（MVP → 完整版）

**MVP（最小可用）**：
- 支持手动触发
- 固定 2 个模型并行
- 基于现有 Agent harness
- 简单交叉验证（同意/不同意）
- Inline 评论输出
- 基础增量（新 commit 重新跑）

**后续迭代重点**：
1. 完善交叉验证与收敛策略
2. 优化大仓库上下文管理
3. 支持用户自带 Key + 项目配置
4. 增加审查质量数据反馈闭环
